# 収集商品のサイト投入：予想される問題と事前に決めること（Claude回答・2026-11-16）

対象：Shoe Palace 158件 → Kith 2,019件 → Patta 113件 → 他店
前提：カテゴリー設定（91カテゴリー）はオーナーの指示なしに変更しない。

## 結論
投入後に直すと全件作り直し・手作業修正になるのは次の4つ。投入前に決める。
1. カテゴリーの付け方
2. 商品の識別キー（SKU）
3. サイズ表記（バリエーション属性）
4. 投入単位で一括取り消しできる仕組み

価格・説明文・在庫は後から一括で直せる。ただし直すための元データ（現地価格・為替・取得日）は今から残す。

## 1. 決めること（Shoe Palace投入前）

### 1-1. カテゴリー割り当て（最優先）
- 現状：インポーターはCSVのカテゴリー欄を読まない。自動分類は末端カテゴリーが付いた商品しか補完しない。このままでは新規投入分はカテゴリー無しになる。
- 案：元データの部門（Men／Women／Kids）とコレクション名から、既存91カテゴリーの末端への対応表を作り、インポーターが読む。カテゴリー自体は増やさない。
- 対応できない商品は公開せず、下書き＋要確認（_nx_catnav_needs_review）にする。
- オーナー判断：キッズを公開してよいか（KIDSは現在0件。公開すると初めて表に出る）。

### 1-2. 識別キーとSKU
- 案：キー＝「店コード＋元の商品ID」（例：SP-123, KITH-456）で全店統一。商品名ベースの重複判定は店が増えると破綻する。
- 決めること：同じ商品（同じ靴）が複数店にあるとき、1商品にまとめるか、店ごとに別出品にするか。Kithで頻発する見込み。
- SKUは注文履歴に残るため、後から変えると追跡が切れる。既存197点のSKUはそのまま。

### 1-3. サイズ表記
- バリエーション属性名と値の書き方を全店共通にする。
  - 大人：US 9
  - キッズ：10C／3Y など（前例なし→今回決める）
  - レディース／メンズの区別
  - アパレル：S〜XL
- 投入後に属性を変えるとバリエーション作り直しになる。

### 1-4. 画像
- 元URL直リンクのままだと、相手側のURL変更・配信停止で大量の画像が一斉に切れる。
- 自サイト（メディアライブラリ）へ取り込むか、直リンクのままにするかを今決める。後からの切替は事実上の再投入。
- 平置き写真の切り抜きメイン化ルールを2,000件規模でも続けるか。

### 1-5. 価格方針（後から直せるが、根拠は今残す）
- BUYMA同額か、自サイトは手数料がない分を下げるか：オーナー判断。
- 今やること：現地価格・通貨・為替レート・取得日を商品メタに記録する。方針決定後に一括再計算できる。
- クーポン価格（FLASH30／FLASH50等）は期限切れリスクがあるため、販売価格の計算には使わない案。

### 1-6. 在庫
- 2026-11-15時点のスナップショット。受注後買付なら、注文時に仕入れ先在庫を再確認する手順が必須。
- 決めること：在庫同期の頻度、売り切れ商品は非表示かSOLD OUT表示か。

## 2. 作ること（仕組み）
| 項目 | 内容 | 担当案 |
|---|---|---|
| インポーター改修 | 対応表でカテゴリー付与／元価格・為替・取得日・店・投入バッチIDをメタに保存／下書きで投入 | Claude（コード）、ミューズ（実行） |
| ドライラン報告 | 実行前に件数・カテゴリー未対応・重複・サイズ揺れ・画像切れを一覧化 | Claude |

| QA更新 | 商品数197の固定をやめ、「公開商品は全て性別＋大分類＋末端あり」を検査。件数は投入記録と照合 | Claude |
| 在庫・価格の再同期 | 識別キーで既存商品を更新（新規として重複作成しない） | Claude（コード）、ミューズ（実行） |

## 3. 投入ごとに毎回やること
1. ドライラン → 未対応カテゴリーとサイズ揺れを解消
2. 下書きで投入（バッチID付き）
3. QA自動検査
4. オーナーが数件を目視確認
5. 公開
6. 投入記録をGitHubに残す（件数・バッチID・失敗分）

## 4. 進め方
Shoe Palace 158件で一通り試し、手順を固めてからKith 2,019件へ進む。
カテゴリー対応・取り消し・QA更新のコードは、1章の方針が決まり次第Claudeが書く。
