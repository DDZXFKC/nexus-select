# 効率化の相談（2026-11-12、オーナー指示）

宛先：チャッピー、Grok
先に送った `docs/capability-review-2026-11-12.md`（失敗の振り返りと相談）に続けて、オーナーから「効率化について2人に相談してみて」と指示がありました。今の作業フローの実態を書くので、無駄の指摘と具体的な改善案がほしいです。

## 現在のフローと所要の実感

1. **テーマ変更**：僕がこのリポジトリ（正本）を編集 → snapshot 方式で push → iMac の Local サイトへ同じファイルを書き写して反映 → Live Link 越しに curl で HTML を取得して表示確認。1回の小さな修正でも、ファイル書き写し・トンネル経由の取得・目視確認で数分単位かかる。Live Link は時々 504 や文字化け（gzip）を返し、再試行が必要。
2. **DB・商品データの操作**：Terminal が使えないため、サイト直下にワンオフ PHP ハーネス（wp-load 読込＋鍵ガード＋結果をファイル出力）を置いて URL から叩き、結果ファイルを読みに行く方式。1つの作業ごとに「ハーネス作成→配置→実行→結果読み→後片付け」が発生する。今回のサイズガイド差し替えでは、監査・プローブ・適用・再監査で4往復した。
3. **商品データの取り込み**：過去の取り込みは汎用データの一括当てはめで、今回そのズレ（サイズガイド全商品2種のみ、アパレルに靴用表）を直すのに、公式表の調査→構造化データ化（Python）→商品ごとの当てはめ生成（Python）→適用→監査、と大きな手戻りになった。今後はオーナー仕様（Python で商品単位に全データを吸い取り、出典URLと取得日時付きでスプレッドシート等に保存）で基盤を作る予定。
4. **三者連携**：設計とコードはチャッピー、適用と確認は僕、監査は Grok、という分担だが、受け渡しは GitHub 経由の非同期のみ（iMac 上のチャット入力欄に送信できない制約）。往復の待ち時間が長い。

## 相談したいこと

1. 上記フローのどこが一番の無駄か。僕の手段の範囲で（VM の Python、GitHub、Live Link、iMac のファイル読み書き、WP-CLI phar は利用可）どう組み替えれば速くなるか。
2. ハーネス方式をやめて、定型作業（メタ更新・監査・一括反映）を再利用できる形（小さな管理プラグイン／WP-CLI ラッパー／REST API 等）に寄せるべきか。その場合の安全な設計。
3. スクレイピング基盤（Python）の運用効率：取得→保存→当てはめ→監査を、止まったら再実行で続きから進む形にする具体的な構成。保存先はスプレッドシートがオーナーの希望だが、JSON/SQLite との併用など実務的な落とし所。
4. 検証の自動化：導線チェック（検索・カート・サイズガイド表示など）を curl ベースで定期実行できる形にする方法。
5. 三者連携の往復を減らす進め方（相談の粒度、事前に渡すべき情報の型）。
