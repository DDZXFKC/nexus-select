# クーポン適用判定の方式について（オーナー提案・2026-11-18）

宛先：GPT（設計担当）。coupon_bridge の適用判定の仕組みの設計入力。

## オーナーの考え（2026-11-18、本人の発言そのままの趣旨）

- クーポンコードのサイトでも、利用条件や利用可能期間は明記されている。
- 100%その規約通りにクーポンが使えるわけではないと思う。
- ただ、いろんなサイトのクーポン情報を集めることによって、使えるクーポン・使えないクーポンが見えてくるのではないか。

## 現行設計との関係

- 現行の coupon_bridge は「発見情報」と「適用確認」を分離し、実測割引のみを適用可として受理し、原価→販売価格へ反映する。
- 収集時にサイトで拾えるクーポン情報（コード・割引内容・利用条件・商品ごとの対象可否フラグ）を必須項目として保存することは既定（2026-11-14/15の決定）。
- 適用判定の仕組み自体は「後で組む（現段階は取得・保存まで）」として保留中だった。本提案は、その判定方式の設計入力になる。
- 発端は Shiekh のクーポン確認。流通コードは多いが公式確認が取れておらず、現行ルールでは価格に反映できない、という話から出た提案。Shiekh 固有ではなく全店共通の方式として扱ってほしい。

## GPTに検討してほしいこと

1. 複数クーポンサイトの情報（コード・割引内容・利用条件・有効期間・成功／失敗の報告・最終確認日）を集約し、一致度や新しさから「使えそう／使えなさそう」を見分ける方式が、適用判定として成立するか。
2. 「発見」と「実測確認」の間に「有力候補」のような段階を設ける設計が妥当か。その場合、価格（原価計算）へ反映してよいのはどの段階からか。現行どおり実測のみに限るか、有力候補も条件付きで使うか。
3. 使えないコードの見分け方（期限切れ・対象外・失敗報告の集約）と、確認できなくなったコードを無効化する既存ルール（定期再確認）との接続。
4. 集約に使う情報源の範囲と、各ショップの収集Python・クーポン管理への組み込み方（既定では商品収集Pythonに連携する共通機能として追加する方針）。
