# 保存の仕組みの提案と、統合案との食い違い（Claude・2026-11-16）

対象：docs/catalog-import-owner-decisions-2026-11-16.md の「4. 相談事項」と「統合案への反映依頼」

## 1. 保存の仕組み：SQLite（1ファイルのデータベース）＋見る用のシート出力

### 提案
- 保存の本体は **SQLite**。iMac上の1ファイル（例：~/ahc-data/ahc.db）。サーバー不要、Python標準で扱える。公開リポジトリには置かない。
- オーナーが見る・確認する用には、実行のたびに**出力シート（xlsx/CSV、またはGoogleスプレッドシート）を自動で書き出す**。見た目は今までのシートと同じ。
- 1個のPythonで「ショップ別収集 → 判定 → 出力」を順番に回せる。

### 段階（＝テーブル）
| 段階 | 中身 |
|---|---|
| ショップ別の収集結果 | ショップごと・実行回ごとの商品・サイズ・在庫・価格（取得日時つき） |
| ショップ条件 | 各仕入先のクーポン条件（コード・割引・対象・最低額・期限・併用可否）、送料など |
| 判定 | 商品ごとに採用ショップと理由（価格などの条件）、買い付け可能な他ショップ |
| 出力 | 採用済み商品だけ（重複なし）。他ショップはセルに記録。サイト投入はここから |
| 手動上書き | オーナーが「この商品はこの店」と決めた分。判定より優先 |

### シートだけの場合との比較
| | SQLite＋シート出力 | シートのみ |
|---|---|---|
| 件数 | Kith 2,019件×サイズでも問題なし | 数万行で重く、API制限あり |
| 履歴 | 実行回ごとに残せる（価格・在庫の変化が追える） | 上書きになりがち |
| 途中で止まった時 | 途中まで確実に保存、続きから再開 | 書きかけが残りやすい |
| 見やすさ | 出力シートで同じように見られる | そのまま見られる（長所） |
| 手で直す | 手動上書きシートを読み込む形にする | 直接直せる（長所） |

代替：段階ごとのCSVファイルでも動くが、ショップが増えると整合が崩れやすい。外部のデータベースサーバーは今の規模では不要。

## 2. 統合案 v1 との食い違い（オーナー決定を優先して直す箇所）

1. **クーポン（最大の食い違い）**
   - 統合案2章A「通常価格で黒字のものだけ販売、クーポンでのみ黒字はHOLD」は、オーナー決定「原価はクーポン適用が基本」と逆。
   - 直し方：仕入先シート（ショップ条件）の条件で適用可と判定できれば、クーポン後の原価で計算する。期限が来たら同期処理が自動で通常原価に計算し直す（または一時停止）。注文時に適用できるかを確認する手順は残す。
2. **重複の扱い**
   - 統合案1章の「正規化マスターで同一商品を束ねる」はオーナー決定（ショップ別Python・判定で採用店を決める）と方式が違う。
   - ただし「同じ商品か」を判定するには、比べる項目が必要。各ショップのPythonが**同じ形式**（メーカー品番・色・サイズ体系・価格・在庫）で出力するようにすれば、共通マスターなしで判定できる。
3. **価格**
   - 統合案の利益下限M・最低売価式は、オーナー決定「自サイト＝BUYMA価格−BUYMA手数料分」で置き換わる。
   - 必要なのは **BUYMA手数料率の正確な数値**だけ（今の式の÷0.745に手数料がいくら含まれているか）。
