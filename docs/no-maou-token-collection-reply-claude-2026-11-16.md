# 魔王トークンに頼らない商品収集：Claude案（2026-11-16）

相談：docs/no-maou-token-collection-consult-2026-11-16.md
前提：docs/collection-methods-per-shop-2026-11-16.md、SQLite正本（L0〜L4）、欠落の統合ルール。GPT案（no-maou-token-collection-reply-gpt-2026-11-16.md）も読んだうえでの独立案。

## 0. 結論
- 収集は「iMac上のPython 1本」が全部やる。魔王ちゃんは実行も監視もしない。読むのは実行後の**1枚の結果報告（数行）だけ**。
- 動かし方は2つで中身は同じ：①オーナーがiMacで `収集を開始.command` をダブルクリック（手動）、②夜間の定期実行（launchd）。**まず①で確実に動くことを完成条件にし、合格してから②を足す。**
- ブラウザ操作が必要だった店は、ブラウザ操作を自動化するのではなく「スクリプトで取れる正規の経路に置き換える」か「対象から外す／低頻度の手作業に残す」かのどちらか。アクセス制限（403など）をすり抜ける自動化はしない。

## 1. 仕組み（全体像）

```
収集を開始.command（手動） / launchd（夜間）
        ↓
ahc_collect.py（共通の入口・1本）
  ├ 店ごとの設定（有効/無効・取得方法・対象コレクション・間隔）
  ├ 取得方法ごとの部品
  │   shopify_json（products.json）… Shoe Palace / Kith / Patta / Notre
  │   embedded_json（ページ埋め込みJSON）… Notre順位 / 6pm
  │   既存コレクター呼び出し … BSTN
  ├ SQLite正本へ保存（L0原本 → L1抽出）
  ├ 欠落チェック（統合ルール：項目別の取得率・参照表の穴）
  └ 結果報告を1枚出力（report_YYYYMMDD.md）＋ 失敗時だけ通知
```

### 1-1. 手動スタートで「ちゃんと稼働する」ための条件
- ダブルクリック1回で動く。引数の入力は不要。
- 画面（ターミナル）に「店名・進み具合・残り件数」が出る。終わると「完了／一部失敗／停止」と報告ファイルの場所を表示。
- 途中で止まっても（Macのスリープ、回線切れ、ウィンドウを閉じた）、**もう一度ダブルクリックすれば続きから**再開する。取得済みの商品は取り直さない。
- 同時に2つ起動しても、2つ目は「実行中です」と出て終わる（ロックファイル）。
- 必要なPython環境はフォルダ内に固定（専用の仮想環境）。iMacの他の設定に左右されない。
- 受け入れ試験：オーナー（または魔王ちゃん）がダブルクリック → Shopify 3店が最後まで取れて、報告が出る。途中でウィンドウを閉じ、再度ダブルクリック → 続きから完了する。この2つが通れば合格。

### 1-2. 無人実行（定期実行）
- launchd で毎日深夜（例：2:30）に同じ入口を起動。iMacのスリープ中でも起こして実行する設定にする。
- 失敗時の自動再開：一時的な通信エラー・タイムアウトは待って数回まで再試行。403・アクセス拒否・規約上の停止は**自動再開しない**（翌日も同じ店はスキップし、報告に「要判断」と出す）。
- ログ：実行ごとに1ファイル（店・件数・エラーの種類別件数）。詳細ログはローカルだけに保存し、GitHubには集計だけ。
- 欠落検出：取得後に項目ごとの取得率を計算。統合ルールの基準（A段階の項目が2割以上欠けたら、その店のその回はL4出力に進めない）で自動判定。
- 結果の保存：L0（生JSON）とL1（抽出）を同じトランザクションで保存。前回より大きく件数が減った場合は「削除」と判定せず、報告に出して止める。

### 1-3. 魔王ちゃんの役割（トークンを使う所）
- 正常時：報告ファイル（数行）を読んで、オーナーに一言伝えるだけ。
- 異常時：報告の「要判断」欄だけ読み、オーナーに判断を仰ぐ。ログ全文は読まない。
- 店の追加・取得方法の修正：コードの修正はClaude（またはGPT）が書き、GitHub経由で渡す。魔王ちゃんは更新と1回の試験実行のみ。

## 3. 規約面の扱い
- 「自動収集禁止」「アクセス拒否」の店は、定期実行に入れない。設定ファイルの `enabled: false` と理由を書いて、間違って有効にならないようにする。
- 代替の順番：①公式・提携の商品データ（フィード）、②低頻度の手作業（人が見て記録）、③対象から外す。
- 判断はオーナー。ただし手作業を続ける店は、それ自体が魔王トークンを使うので、売上への寄与が小さければ③を勧める。

## 4. 優先順位（トークン削減効果の大きい順）
1. **Shopify 3店（Kith 2,019件・Shoe Palace・Patta）**：件数が最も多く、すでにスクリプトで取れている。入口1本と手動スタートを作るだけで、魔王の実行管理がゼロになる。最初にやる。
2. **Notre**：同じShopify部品の延長で済む。
3. **BSTN**：既存コレクターを入口から呼ぶだけ。許可管理の整理が必要。
4. **6pm**：規約確認後。
5. **Converse・Foot Locker**：自動化しない。代替経路の確認だけ。

## 5. GPT案との違い
- 方向は同じ（AIを実行から外す、既存コードを入口でまとめる、手動起動で合格してから定期化）。
- Claudeは「ダブルクリック1回・閉じても再ダブルクリックで続きから」という手動スタートの受け入れ試験を具体的に決めた。
- Foot Locker・Converseは自動化の対象にせず、提携データ提供の確認か低頻度の手作業か対象外の3択に整理した。
