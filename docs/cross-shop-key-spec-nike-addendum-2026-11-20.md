# 横断キー仕様 追補：Nike法則（nike_fl_v1）

出所：GLM判断（2026-11-20、コーディネーター確定）。本編 docs/cross-shop-key-spec-glm-final-2026-11-20.md への追補であり、corr仕様への nike_fl_v1 追加を承認するものである。
根拠：NIKE.com実ページ照合で10件中10件一致・反証0件（第一級証拠5件を含む）。
以下はGLM判断の全文である。

---

## 判定

**確定と認定する。ただし適用範囲を正規表現ゲートで限定し、下記の留保を仕様に刻むことを条件とする。**

2026-11-20時点の「確定ペア0件につき外挿禁止」は、確定ペアの不在を理由とする判断でした。本次第で第一級証拠5件以上・反証0件が提出されたため、禁止を解き、条件付きで確定ペアとして扱います。

---

## 1. 証拠評価：直接4＋間接6という構成について

まず「間接6件」は均質ではないので、私の方で再階層化します。

| 証拠階層 | 該当番号 | 評価 |
|---|---|---|
| A：第一級（nike.com現行ページ直接読取） | #6, #7, #8, #9 | Style CodeをNike自身のページから読んだもの。存在証明として十分 |
| B：第一級準ずる（nike.com URL内コード） | #4 | URLパスにSKUが埋め込まれているのはNike自身の発行物。販売終了でも証拠強度はAに近い |
| C：第一級背景＋断片 | #2 | ページ存在は第一級だがStyle読取がBingスニペット経由。転写経路が一段入る |
| D：第三者（GOAT/StockX等） | #1, #3, #5, #10 | SKU転写は実務上信頼できるが非権威。補強材料としてのみ扱う |

**判断の根拠：**

- この法則は決定論的な変換規則であり、反証1件で崩れます。10件中10件一致・反証0件、かつ第一級が5件あるのは十分です。
- 落とされる先頭英字が I・F・D・J と4種に分布している点が重要です。「特定の文字を落とす」ではなく「先頭1文字を落とす（文字種無関係）」という一般則として成立します。
- `B0018004`（IB0018-004）のように内部ゼロが保存されていることも確認済みで、文字列変換則として整合します。

**ただし正直に限界も記録します：**

- 検証可能だったペアは「法則が成り立つものほど見つけやすい」という選択バイアスがあります。検証不能のまま残った個体こそ runtime 側の防御が本番です（後述の反証プロトコル）。
- サンプルは現行世代の「先頭英字2文字＋数字4桁」SKUに偏っています。レガシー形式（全面数字スタイル等）への外挿は引き続き禁止です。

## 2. corr仕様への追加（照合方向とキー生成）

前提の確認：FL→公式方向で先頭英字を復元できない、というご認識は正しいです。ただし**Nike側でキーを派生すれば復元は不要になります**。これが本追加の骨子です。

**正規化パイプライン（双方向共通）**
```
normalize(s): 全角→半角、大文字化、空白・ハイフン類（- ‐ – − ー）の除去
```

**適用ゲート（この外は「未検証」として旧来どおりキーを生成しない）**
```
Nike SKU: ^[A-Z][A-Z0-9]{5}-[0-9]{3}$   （正規化後、ハイフンは保持して判定）
FLコード: ^[A-Z][0-9]{7}$
```

**キー生成（非対称）**
- 正方向 Nike→FL：決定的。`normalize(SKU)からハイフン除去 → 先頭1文字除去` で8桁の派生キー K1 を生成。**自動キー生成を許可**。
- 逆方向 FL→Nike：FL側は無変換（正規化のみ）。NikeカタログをK1で索引化し、FLコードで**完全一致検索**。ご提案の数字7桁コアは K2（`末尾7桁・先行ゼロ保持・文字列型`）として副次索引に回す——K2はタイポ許容や衝突監視用。

つまり「数字コアでの索引検索」ではなく「**派生キーへの完全一致**」を主経路にできます。FL側の頭文字＝Nikeスタイル2文字目が保存されているため、K1は10件すべてで機能しています。

**多重ヒット処理（K1・K2とも）**
- `AB1234-100` と `XB1234-100` のような接頭衝突は構造的に起こり得るため、候補が複数なら自動リンク禁止。
- 絞り込みは優先順位をつけて：①カラーのトークン類似度（Shown対比。**タイブレーク専用でハードフィルタ禁止**）→ ②モデル名トークン重複（#1の「Low LE」対「'07 LV8」の事例が示すとおり、これもフィルタ禁止）→ ③価格差トリップワイヤ。解決しなければ `status=ambiguous` で人力キュー。

**スキーマ・運用**
- ペアに `xref_rule: nike_fl_v1`、`evidence_tier: A–D`、`matched_key: k1|k2`、`candidate_count` を付与。
- 提出10件をゴールデン回帰ケースとして固定（#2のゼロパディング案例、#1の名称乖離案例を必ず含める）。
- キー構築時にK1衝突件数をレポートすること。
- **反証プロトコル**：第一級証拠による反証1件の確定で、該当パターンクラスの法則を即座に「停止」へ降格。決定論的規則なので多數決はしません。

## 3. 条件・留保

1. **間接確認分の扱い**：D階層（GOAT/StockX出典）は補強であり、今後の新パターンクラスの根拠には使わない。販売終了品がスコープに入ることの正当化には足りるが、係争時の権威としては扱わない。
2. **トリップワイヤの適用範囲**：
   - 適用対象は自動リンク済みペアのみ、かつ**双方に現行公式価格がある場合のみ**。販売終了品は `price_unverified` フラグでスキップ（最終既知MSRPが蓄積されているなら、拡幅バンドでの比較は任意）。
   - **GOAT/StockX等の市場価格はトリップワイヤ入力から排除**（プレミアム載せのため誤爆する）。
   - トリップワイヤ発火＝自動公開ブロック＋レビューキュー。法則由来リンクでの発火率が閾値を超えたら反証プロトコルへ接続。
3. **型の安全性**：K1/K2は常に文字列型。数値キャストで `B0018004` → `B618004` 的なゼロ落ちが起きる実装はバグとして回帰に登録。
4. **サンプル規模**：決定論的変換則の確認としては10件で足りるが、エッジケースの主張には薄い。実運用の安全網は上記監視（ambiguous率・トリップワイヤ率・反証キュー）であり、仕様書にその旨を明記。
5. **SKU形式変更**：Nikeが接頭文字数等の形式を変えた場合は本法則の再検証を開く（四半期ごとに第一級5件の抜き直し確認を推奨、必須ではない）。
