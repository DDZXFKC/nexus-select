## 結論サマリ（先に4問ぶん）

1. **横断キー**：`正規化ブランド::正規化型番（色コード込みフル一致のみ）`。型番なし商品は横断対象外。
2. **採用判定**：仕入総額最小 → タイブレークは鮮度→確度。在庫の本気確認は「受注後の買い付け時」に寄せる。
3. **順序**：FLの原価計算が先。横断の仕組みは後。BSTNは最後でよい。
4. **出力層**：横断レイヤーはステートレス変換（都度CSV読み込み）にし、統合DBは作らない。ジェネレータの入力を横断出力CSVに差し替えるだけ。

## 1. 横断キーの具体仕様

```
cross_key = norm_brand(brand) + "::" + norm_model(model)
```

- **norm_brand**: 大文字化→空白正規化→別名マッピング（必要になったら追加。最初は空でよい）
- **norm_model**: 大文字化 → `-` `/` 空白をセパレータ扱いで `-` に統一 → 前後空白除去
- **SKU接頭辞は横断レイヤーの責務にしない**。各ショップの取り込み時点で剥が済みの生型番だけを扱う。横断レイヤーにショップ知識を持ち込まないのが最小構成
- **色違いの扱い**: Nikeの `DD1391-100` は色コード込み。BUYMAでは色違いが別出品になるので、キーは**フル型番（色コード含む）の完全一致のみ**。部分一致によるあいまい統合は誤統合→価格計算破壊のリスクが大きいので導入しない
- **型番なし商品（アパレル等）**: **横断対象外、ショップ単独で出品**。理由：(a) フォールバックキー（タイトル正規化等）は精度が落ち誤統合の元、(b) アパレルは同型番でも仕様がズレる、(c) オーナー方針「過剰な仕組み化をしない」。将来の拡張案として「ブランド＋正規化タイトル＋色」のフォールバックは仕様書に一行残すだけにする
- **Converse**: キー生成・価格計算には含める。出品レイヤーで `block_until=2026-12-25` フラグを付けて止める。差止明けに即日出せる状態を作っておく

## 2. 採用先の判定ロジック

- **第一判定**：クーポン後仕入総額（送料込み）の最小。既存決定3と整合
- **タイブレーク順**（辞書式ソートで実装終わり）：

| 優先 | 項目 |
|---|---|
| 1 | 仕入総額（安い方） |
| 2 | スナップショット日付（新しい方） |
| 3 | 販売可否・原価の計算済みフラグ（verified の方） |
| 4 | 固定ショップ優先順位（SP > FL > Notre…と決めて打ち切り） |

- **在庫の扱いは分離する**：採用判定ではスナップショットの在庫フラグをフィルタとして使うのみ。本命の在庫確認は**受注後の買い付け時**に個別実施。ここはオーナーが時間をかける方針の「買い付けの自動化」と直結する箇所なので、定期再クロールのような過剰な仕組みに投資しない
- **再確認は定期実行しない、トリガー式**：(a) バッチ生成時に採用候補のみスポット確認、(b) BUYMA受注時にその商品のみ。全ショップ常時監視はコストに見合わない
- 鮮度は各レコードに `snapshot_date` を持たせ、判定結果に `as_of` を添付。再計算は明示トリガー時のみ

## 3. 作業の順序

**FLの原価計算が先。横断の仕組みが後。** 理由は単純で、採用判定は「比較対象のデータ」がないと動かない。横断キーを先に作ってもテストデータがSPしかない。しかもFLの計算はSPで確立済みパイプラインの適用であり新規開発ゼロで早く終わる。

| 順 | 作業 | 理由 |
|---|---|---|
| ① | FL 販売可否・原価計算 | 既存パイプライン適用。データ完成が仕組みの前提 |
| ② | 横断キー生成＋採用判定の最小実装 | SP＋FLの2ショップでまず動かす |
| ③ | バッチ3を横断出力から生成 | 接続検証 |
| ④ | Notre商品マスター統合 | CSV＋タブ構造が既にあるので機械処理可能、バッチ4以降の種 |
| ⑤ | BSTN棚卸し・Converse差止明け対応 | BSTNは正本がiMac側で現物確認コストが高い。商品プールは①〜④で足りている |

横断キーの**仕様確定（この文書レベル）だけは①と並行で先に済ませてよい**。実装は①の後。

## 4. 出力レイヤーの形

- **横断レイヤーはステートレス変換にする**：各ショップCSVを都度読み込み → キーでグループ化 → 採用判定 → 出力CSV（1商品1行＋代替ショップの情報列）を吐く。**中間統合DBは作らない**。これは決定4（ショップ分離保持・最上位のみ統合）と整合し、ショップCSVの更新が自動で反映され、不整合の発生源がなくなる
- 件数は千件規模なのでパフォーマンス設計は不要。pandasでもループでも動く
- **ジェネレータ接続**：入力形式は「1商品1行」のはずなので、入力を横断出力CSVに差し替えるだけ。バッチ3以降は横断出力から生成可能
- バッチ1・2のSP分20件との重複は、`already_listed` の cross_key リストで除外
- **最大リスクは誤統合**（別商品が同キーに潰れる）。最初の1回だけ、横断統合結果のdiffレポート（何と何が統合されたか）を人目で確認する工程を入れる。以降は新規キー追加時のみ
