# Grok による指示書 v3.0 の訂正と v3.2 評価（2026-11-14 受領）

受領経路：Grok 共有リンク（ユーザーがチャットで提示）。転記：魔王ちゃん。
対象：Pythonスクレイピング開発・実行指示書 v3.0（4a1cf3b2）への訂正依頼に対する Grok の回答。

## 1. Grok の訂正版 v3.1 の要点

修正方針（Grok 提示）：
- 「停止しやすい表現」「確認待ち・報告待ち」を極力排除
- エラー発生時の判断基準を明確化し、停止範囲を最小化
- サイクルを「実行優先」に再設計
- AI間の役割分担を「待ちが発生しない」形に調整
- 即時実行命令を強め、「完成待ち」を排除

v3.0 からの主な変更点：
- 絶対厳守ルールに「完璧な状態になるまで実行しないことの禁止」を追加
- 実行手順から「修正結果を確認する／次の対象へ進む」の二段を統合し、禁止事項として「エラーごとの停止・全件再実行」「1つの問題で他の処理を止める」「レビュー待ちで収集を止める」を明記
- 再試行エラーは上限を超えたら「続行するエラー」として記録し次へ進む、と明確化
- 役割分担に「レビュー結果を待たずに並行して進める」を追加
- 報告ルールに「報告のために実行を止めることを禁止」を追加
- 即時実行命令に「準備が整っていない・レビューが終わっていない・設計を固めてから、を理由に実行を遅らせることを禁止」を追加

## 2. GPT の v3.2（統合済み）への Grok の評価

GPT が5点（取得と解析の分離、エラー原因調査の自動化、共通障害の停止基準＝致命的解析エラー5件連続で該当処理を保留、収集と修正の並行、実行時間の計測）を追加して v3.2 とし、91486afe で統合済み。これへの Grok の評価：

- 総合：「ほぼ正しいが完璧ではない」、80〜85点。このまま v3.2 で進めて問題ない。
- 弱い点5つ：
  1. 「完成」の定義が曖昧。店舗単位で「実務で使える最小完成状態」を先に定義する（例：BSTNで商品名・価格・サイズ在庫・画像URLが安定して取れる状態）。
  2. データ品質の下限が弱い。価格・在庫・品番は、一定のエラー率を超えたらそのカテゴリを保留する基準を追加する。
  3. 優先順位の欠如。店舗・カテゴリ・商品群にビジネス優先度を付ける。
  4. 保存HTML依存のリスク。有効期限（例：24時間）を設け、古いHTMLは再取得する。
  5. 計測の粒度。通信・解析・保存に加え、1商品あたり平均処理時間とエラー率をセットで見る。

## 3. 仕事の進め方プロンプト v3 への Grok の指摘

ユーザーが v3 を Grok に渡し、Grok が問題点5点を指摘した（修正版の作成提案で終了、全文は未提示）：
1. 「作業前にチャッピーの指示を仰ぐ」が強すぎて確認待ちで止まる。
2. GPT→Grok→魔王ちゃんの直列フローが「待ち」を再導入している。
3. 「必須項目がすべて合格してから次へ」と「独立作業を止めない」が矛盾しやすい。
4. 途中経過の報告が曖昧で、報告のために手を止める可能性がある。
5. 「ユーザーを伝言役にしない」が徹底しきれていない。
改善方針：確認は開始時の1回だけと明確化し再確認を禁止、コードフローは可能な限り並列化、「合格待ちで独立作業を止めない」を優先ルールとして明示、報告は「止まったときだけ理由を伝える」に寄せる。Grok は v3 の改訂版（実行継続性強化版）の作成を提案し、本人の回答待ち。
