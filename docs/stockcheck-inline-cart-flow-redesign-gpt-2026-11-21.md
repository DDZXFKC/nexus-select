# 在庫確認：その場で判定→カートへ進む方式（2026-11-21 オーナー決定）GPT実装設計

**優先順位：このオーナー決定が、メールで結果を返す決定3・Claude最終設計（メール方式）より新しい。** 旧メール送信5分ルール、受付・90日保存・メールテンプレート・遅延ワーカーは新方式の本体から外す。XServerがサイト正本。コードを本番へ反映したとは記載しない。

## 1. ユーザー操作（サイト担当：Claude、実装連携：GPT）

1. 商品ページでサイズ（必要な商品ではカラーも）を選択。「在庫を確認する」を押すと、ページ内モーダルを開く。**メッセージ欄にサイズは記入させない**。
2. モーダル内に選択商品・サイズ・カラーと価格変動の5事案（既存オーナー決定に基づく）を表示。「在庫を確認」を実行。処理中はスピナーと「在庫を確認しています…」を表示。多重クリック不可、閉じても非同期処理は安全に終了または破棄する。
3. 結果：`IN_STOCK`かつ価格確定・購入許可が有効 →「在庫確認できました。カートへ移動できます」。同じ選択サイズを**カートへ入れてから**カート画面へ移動（または「カートへ入れる」→「カートへ進む」の2段階）。`OUT_OF_STOCK` → 選んだサイズだけSOLD OUT表示、購入不可。`UNCONFIRMED`/通信障害 →「現在、買い付け先の在庫を確認できませんでした。時間をおいてもう一度お試しください。」SOLD OUTの確定表示はしない。
4. 名前・メール入力は**即時在庫確認の必須条件としない**。旧ポップアップ仕様での個人情報収集はメール結果通知に必要だったもの。新方式で依然必要とするなら目的・必要性をClaude側と協議してから別設計にする。問い合わせ受付IDやメール送信を結果の条件にしない。
5. 以前の確認結果では購入できない。ページリロード、サイズ・カラー変更、許可の期限切れ、価格変更などで購入許可を再確認する。

## 2. API・セキュリティの実装境界

- 推奨経路：WordPress AJAX/REST の認証不要でも呼べる**必要最小限の公開判定エンドポイント**。入力は商品ID、variation ID、選択サイズ・カラー、CSRF防御用nonceおよび一意リクエストID。ブラウザに買付先URL、原価・秘密情報、管理者APIキーは出さない。
- WordPressが選択サイズ/カラーとvariation IDの一致を**サーバー側で検証**。PythonのStockChecker/OfferResolverをサーバー内部から呼ぶ（cronで後追いして結果をメール送信する方式は採用しない）。PHPのHTTP処理とPython実行可否はXServerで検証して接続方式を確定。タイムアウト・アクセス制御・同時アクセス上限を設ける。
- 在庫確認が真正に成功した場合のみ、**サーバー側に紐付く購入許可**を発行。許可キーはランダム・短命・一回使い切りで、商品ID、variation ID、サイズ、カラー、選択仕入先、確定販売価格、期限、セッションとの紐付けを保存。URL改ざん、スクリプト書換え、別サイズ・別顧客への流用を防ぐ。
- WooCommerceの通常のadd_to_cartとStore API/ブロックカート双方の**サーバー側入口**で、許可を検証。単にフロント側のボタンを有効にするだけでは不可。購入許可がなければカート追加を拒否。WooCommerce `woocommerce_add_to_cart_validation`、`woocommerce_store_api_validate_add_to_cart` 等の実装経路をXServer上で確認。
- 購入許可の寿命は**提案値5分**（オーナー確定ではない。実装パラメータ）で、期限切れは再照会。カート投入時に価格決定を保存し、カート再計算・注文作成時にもサーバー側で価格が正しいか検証。**既存カート全体を解放する`ahc_stock_check_allow_cart=true`は禁止**。
- 取得失敗/403/429/価格不明/原価不明なら許可は発行しない。ボット対策の回避禁止。失敗をSOLD OUTと誤表示しない。一定回数/同一IPの流量制限、証跡・エラー管理ログを用意。

## 3. 現在価格と400円ルールの新しい適用

**StockChecker**：選択した同一サイズ/色の在庫と現地現在価格を、同じ買付先ページ取得から読む。確定できなければ`UNCONFIRMED`。複数買付先は候補の原価見込み順に確認し、在庫ありで実価格を確保できたものについて**比較可能な着地総原価**と再計算販売価格を得る。安値一択は表示価格と販売可能価格の条件を明示して判定。サイトの商品価格を恒久的には書き換えない。

**PricingPolicy**（`tools/stockcheck_inline_price_policy.py`）：
- 再計算販売価格（現在価格・適用可能クーポン・為替・現地送料・現地税・関税・輸入消費税・代行費・販売/決済手数料等が揃った計算結果）が掲載価格以下 → **掲載価格でカート追加可**。
- 掲載価格より高いが差額1〜399円 → **掲載価格のままカート追加可**。差額は店舗負担。
- 差額400円以上 → モーダルに「在庫確認できました。現在の購入価格は◯◯円です（掲載価格△△円）。この価格でカートに進みますか？」と**明示同意**。承認後、選んだvariationだけ◯◯円でカート追加（選択時点の価格同意とサーバー保存価格が一致していること）。
- 最新価格または必要経費が不明 → 販売価格を決定できないため**カート不可**。在庫不明/価格未確定をSOLD OUTとはしない。
- 価格差0/399/400円境界、クーポン失効、元の商品表示価格との差、再訪時の不一致を自動テスト。
- **注意**：価格計算の正本関数・丸めルールは現行XServer/商品管理の決定価格ルールを読み、既存関数を再利用する。BUYMA用の価格式を自社ECへそのまま転用しない。試算額を決済価格として確定させない。

## 4. リアルタイム性能と失敗時の扱い

- メール方式の「結果メール5分以内」は**取り下げ**。画面内のスピナーは判定要求中だけ出す。現在のオーナー決定には「画面判定何秒以内」という確定上限はないため、**5分間スピナーを回し続ける設計にしない**。
- 推奨：HTTP取得10秒/店舗・短い即時再試行1回まで。全体タイムボックス30〜60秒を設計上の**暫定上限**として設定可能にし、超過したら「確認できず／再度お試しください」を表示。これはオーナー決定値ではない。長時間処理時の通信切断・PHPタイムアウトはXServerで実測検証。
- 30分キャッシュは過去の実在庫確定情報の補助でしかなく、**カート投入許可を過去キャッシュだけで発行してはならない**。買付前の再照会・売切れ時の表示処理が必要。旧StockCheckerは`IN_STOCK`を30分キャッシュする仕様なので、許可ゲート側は在庫ありの場合`use_cache=False`を原則とする（実アクセス負荷に留意）。
- 一店が403/429でも他店は続けられる。候補にUNKNOWNが残る場合、全店OOS判定にしない。

## 7. 追加オーナー決定：在庫あり時のポップアップ内カートボタン（2026-11-21）

- **オーナー確定**：在庫確認に成功したら、ポップアップを閉じなくても同じポップアップ内に「在庫確認できました」と**カートボタン**を表示する。押すと確認した商品・カラー・サイズをカートへ追加し、そのままカート画面へ進める。ポップアップ外にだけボタンを出す実装では不合格。
- `LISTED`：掲載価格でカート投入できる状態なら、メッセージ「在庫確認できました」と「カートへ進む」ボタンを表示。
- `QUOTE_CONFIRM_REQUIRED`：400円以上高い再計算価格と掲載価格をポップアップ内に示し、お客様が**新価格に明示同意した後だけ**同じポップアップ内のカートボタンを有効にする。同意前はボタン無効／非表示。
- `OUT_OF_STOCK`：指定サイズをSOLD OUT表示し、ポップアップ内のカートボタンは表示・有効化しない。
- `UNCONFIRMED`／`PRICE_UNKNOWN`／通信失敗：カートボタンを有効化しない。理由を表示して再確認を案内。
- カート投入はボタン操作時の**サーバー側購入許可検証**（選択サイズ・variation ID・価格・セッション・期限・再使用禁止）を必須とし、成功時にカートへ遷移する。カート投入API失敗なら画面は成功と偽らず再試行案内。
- 結果に遅れて到着した旧リクエストやサイズ変更後の確認結果は採用せず、古いカートボタンを使用できないようにする。
- **受入確認**：実際のXServer商品ページで、在庫あり→同一ポップアップ内ボタン表示→ボタンを押す→**選択したサイズの商品が決めた価格でカートに入っていること**を確認。400円境界、品切れ・不明・二重クリック・戻る操作も確認する。
- **担当**：ClaudeがUIとXServer実機検証を担当、GPTがPython判定・Woo側購入許可APIの整合を担当。これは追加仕様の登録であり、XServer実装完了の証明ではない。

## 8. 追加オーナー決定：ポップアップの個人情報入力を完全廃止（2026-11-21）

**オーナー決定：名前・メールアドレス・メッセージの入力欄はすべて廃止する。** メール結果返信を廃止したため、ポップアップは「選択済み商品・カラー・サイズの確認／判定中スピナー／在庫確認結果／価格差400円以上の同意／成功時のポップアップ内カートボタン」のみとする。

- 名前・メールアドレス・メッセージ、メール確認欄、送信フォーム、受付完了メール、受付ID表示は不要。**問い合わせの個人情報必須バリデーションを在庫確認APIで呼ばない**。
- 入力値は商品ページ上で選択済みの product_id／variation_id／size／color のみをサーバーで再検証。ブラウザ上の指定はそのまま信頼しない。
- 判定開始→スピナー→IN_STOCKの場合「在庫確認できました」と同じポップアップ内に「カートへ進む」。クリック後、選択バリエーションを適正価格でカート追加し、カートへ遷移。
- 価格差400円以上は新価格を明示して同意後にカートボタンを有効化する。それ以外は掲載価格。品切れは該当サイズのみSOLD OUT、確認不能は再試行案内で、いずれもカート許可しない。
- 氏名やメールを収集せず、判定ログに不要な個人情報を残さない。セキュアな短命購入許可トークン、セッション単位の検証・レート制限は維持。
- 以前追加した `tools/stockcheck_inquiry_contract.py` と `tests/test_stockcheck_inquiry_contract.py` は**旧メール問い合わせ専用の遺留コード（新フローでは使用禁止）**。サイト判定経路に接続しない。新実装時に削除・隔離する。
- **Claude担当**：XServerのポップアップUIから全入力欄・旧フォーム送信・メール案内を削除し、実商品画面でスピナー、結果表示、カート遷移を検証する。**GPT担当**：サーバー側のPython判定・価格・購入許可、Wooのカート投入ゲートをこの契約に合わせる。
- 受入テストでは名前・メール・メッセージ未入力で正常に在庫判定→カート投入できることを検証。旧メールフォームに戻さない。

## 9. オーナー補足：個人情報入力は購入画面から（2026-11-21）

- **オーナー確定**：名前・メールアドレスなどの購入者情報は**購入画面（WooCommerceチェックアウト）で初めて入力**する。在庫確認ポップアップ・在庫判定API・カート投入前には求めない。
- ポップアップは選択サイズの即時在庫判定、スピナー、確認結果、必要な価格同意、ポップアップ内の「カートへ進む」ボタンだけを扱う。カートへの追加・カートページへの遷移までは個人情報入力を要求しない。
- 買付先への照会とWooCommerceカート追加の安全性は、商品・variation IDとブラウザの匿名セッションに紐付けたサーバー側購入許可で確保する。顧客氏名・メールを許可トークンの条件にしない。購入者情報はWooCommerceチェックアウトの既存フォームで取得する。
- 旧 `stockcheck_inquiry_contract.py` の名前・メール必須規則は使わない。実画面受入で **未入力のまま在庫確認→カート投入→カート表示→購入画面で初めて入力** を検証する。
- オーナー決定と実装提案を分ける：個人情報入力を購入画面に限定することは**決定事項**、匿名セッションの安全な許可トークン方式は**GPTの実装案**。
