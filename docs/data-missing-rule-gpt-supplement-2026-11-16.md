## 確認した事実
Shoe PalaceはShopify collection products.jsonで163件取得（投入158件とは段階が異なる）。variant SKU、価格、available、画像、body_html、生JSONとCSV保存済みとの報告。cmは元データに存在しない。UGG乳児1C/2C/3Cに対応する公式cm値が換算表にないことが投入準備段階での欠落原因。スクレイピングの取りこぼしではない。収集方法を変更してcmを再取得するという対策は不適切。公式ガイドに値が存在しないケースと、表の転記漏れは区別して記録する。
## 統合ルールへの訂正
1. 欠落の分類を取得元の仕様（SOURCE_SCHEMA_ABSENT）、未取得、抽出失敗、補完元未掲載（REFERENCE_NOT_PUBLISHED）、換算表未対応（REFERENCE_MAPPING_MISSING）、変換失敗、投入失敗に分ける。元ページに存在しない項目を抽出失敗に数えない。公式未掲載は対象ガイドを確認した証拠が必要。
2. 店別の取得能力表を維持する。各項目の取得元、元フィールド、取得可能性、補完先、必須条件、取得日時を記録。Shopifyのcmは外部補完項目。availableは当該店の観測時の販売可否で実在庫数量と同義ではない。body_htmlは素材・仕様の記載有無を検査し、画像はvariantとの対応と利用条件を別に確認。
3. 収集前に店別取得能力表と補完用参照表を準備。抽出後、全variantの原サイズ・対象・体系を列挙し、換算表との突合で未対応サイズを検出する。公式値のないサイズを別ブランドや一般換算で埋めない。原表記を保持し、KIDS cm併記の例外は統合協議で決定。欠落variantのみ保留、正常分を継続。公開済みUGGは今回修正しない。
4. BSTNはSQLite既存観測を再利用。NotreはinitDataの順位とproducts.jsonの価格を同一IDで突合。Converse一覧取得は商品詳細不足を別キューで補完。Shoe Palace/Kith/Pattaは許可済みShopify経路を維持し、保存JSON再解析を優先。6pmはproducts.listと商品詳細の一致・不足検証。Onitsukaは件数のみ、未収集扱い。Foot LockerはHTML/拡張の実績を記録するが、オーナー指示は販売店の許可を代替しない。禁止された自動取得の再実行やアクセス制限回避は行わない。公開エンドポイントも自動収集・商用利用許可と同義ではない。
5. GLM sourcingと実績のある店別収集を混同しない。新システム開発・全面改造は不要。既存Pythonの項目別検査・補完・出力前ゲートの最小差分を優先。
6. 収集数163→投入158の差は別工程として記録、理由は報告資料から未確認。BSTNの2172も今回報告の数値であり過去のシート行数2772やユニークID2419と同じ母集団と断定しない。各段階のrun ID/対象/件数定義を残す。
## 結論
取得可能な情報を一度で取得し、元データにない情報は別経路で補完する。取得方式をむやみに変更せず、欠落の発生段階を特定してその段階だけ直す。統合案に反映を依頼。
