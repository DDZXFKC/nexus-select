# クーポン共通機能・実装第1段階（GPT、2026-11-17）
オーナー制作開始指示、docs/coupon-python-owner-decision-2026-11-17.md に従う。既存3系統は維持。商品収集の内部共通機能として実装し、売れ筋側から参照、サイト点検は独立。既存コレクターや本番DBは変更していない。

## 実装済み
- collector/coupon_bridge.py: Python標準ライブラリのみ。既存L2収集SQLiteの明示的パスを受け取り、名前空間付き2テーブルを追加する。発見情報と適用確認を分離、店別、履歴保存、同一イベントの再実行は冪等。既存RawCouponを候補として取り込む record_raw() を用意（ショップ未特定・コード未特定は手動確認エラー）。既存ソースを新規に書き直さない。
- context(): 店、variant、通貨、配送地域、匿名アカウント識別子、数量、現在の割引前商品小計、カート条件識別子で照合。
- record_check(): 適用条件・利用回数が確認済みで、時差付き有効期限がある実測割引価格のみAPPLICABLEとして受理。未知・失敗を保存可能。証拠参照必須。
- select(): 最新の適用確認、期限、確認鮮度、条件変更、新しい失敗、同時刻の矛盾を確認。条件を満たした中で最安の実測商品小計を選択。併用を推測しない。通常小計も保存・返却。sale_approvedは常にFalse（販売可否は別ゲート）。

## 次の接続作業（GLM実装、Claude支援、GPT監査、Muse実行）
1. 既存の店別SQLite正本の実パス・テーブル仕様を照合し、同じDBに追加する。開発テストではコピーを使用。上記テーブル名は既存との衝突回避のための実装名であり、新しい独立DBを作る決定ではない。trend_items.dbは参照IDと計算時点の記録だけ。
2. 既存 ahc.coupons の許可済みソースを record_raw に接続。全sourcesは現行設定で無効。RetailMeNotはAPI未実装、mydealzは店未特定の候補を返す。未特定候補も原本/要確認キューに残す処理を接続側で実装。取得禁止・制限を回避せず、有効化は許可確認後。公式プロモーションを優先し、手動保存済み情報の入口も用意する。公式条件で適用確定する場合の判定アダプターは追加実装。
3. 商品収集のSTARTから必要なクーポン更新を呼べるようにし、クーポンのみ更新/再計算モードも付ける。収集失敗を独立隔離。現行ahc_collect.pyの欠陥修正と競合しないようGLMが統合差分を作成。クーポン側だけで全商品を再取得しない。
4. 商品・売れ筋の両側から同じ select() を呼び、通常/割引後の商品小計を既存全費目原価計算に渡す。商品小計は着地原価ではない。複数商品カートの割引配賦は未実装なので、現段階は単一SKU・単一条件の正確な小計を渡す。証拠参照や確認フラグの真実性は取得アダプター側で確認する。利用回数の予約/消費管理や購入時の再検証は未実装。
5. 同じ保存DBで両Pythonが同一価格を返す結合試験、条件変更/失効時の原価再計算、買付候補の切替、既存の出品ゲート、再起動、失敗時の独立継続を検証。その後、許可済み1店舗から新規クーポンを実取得→保存→適用確認→原価出力の実機試験を行う。成功の証拠がなければ実店舗合格としない。
