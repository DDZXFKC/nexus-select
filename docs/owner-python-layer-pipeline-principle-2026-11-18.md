## 設計原則
既存の「まずふるいにかけて分母を小さくする」原則（owner-layered-filtering-development-principle-2026-11-18.md）に加え、判定条件だけでなくPythonの責務自体をレイヤー化する。
- 店舗ごとの構造化データの違いは、店舗/構造別の独立した取得・変換Pythonで吸収する。同一構造の共通部品は再利用し、重複コードを増やさない。
- 各Pythonは入力、出力、責務、エラー契約を明確にし、後段は前段の内部実装を知らなくてよい。共通スキーマで接続し、商品ID・店舗ID・市場・取得日時・根拠を引き継ぐ。
- 最終的には各処理を依存順に一列につなぐ。店舗別取得は互いに独立なら並行可。共通後段は順次実行し、対象を段階的に絞る。例：店舗別取得・変換→共通データ→安価な選別→国内価格比較→必要な候補のクーポン評価→総原価/利益判定→承認済み商品登録。既存仕様に合わせて順序・分岐を検証し、例示を無条件の新仕様にしない。
- 独立して開発・単体検証でき、統合時は入出力契約と回帰をテストする。店舗変更で全体を書き直さず、エラーを隔離し、成功分を保存し、必要な差分から再開できるようにする。
## 重さへの懸念と対策
Pythonファイル/モジュールの分割そのものと、プロセス分割による負荷を区別。原則として同一プロセスの関数/モジュール呼び出しで軽量に接続し、独立プロセスは実測上必要な場合のみ。中間データの全件コピー、繰り返しDB書込、ブラウザの無用な再起動、同一情報の再取得を避ける。店舗並列数は資源・サイト規約・許可に従い制限。速度改善は推測で断定せず、同じ保存済みfixtureで処理時間・ピークメモリ・入出力件数・結果一致・再実行コストを比較する。
## 既存資産を先に確認する
既存の店舗別取得コード、保存済みHTML/JSON、店舗構造調査、共通スキーマ、現在の3系統Pythonの接続点を棚卸しし、すでに実現している部分を作り直さない。構造差が原因の不具合を優先して、最小差分で契約と境界を明確化する。クーポン入口の現在の実装指示（coupon-python-implementation-start-2026-11-18.md）は維持し、サイト完成を止めない。
