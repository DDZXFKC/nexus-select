# オーナー決定（2026-11-16）：価格方針と商品重複の扱い

対象：収集商品のサイト投入に関する3者統合案（GLM／GPT／Claude）へのオーナー判断。

## 1. 自サイトとBUYMAの価格差は「手数料の違い」
- 自サイトの価格は、BUYMA価格からBUYMAの販売手数料分を差し引いたものとする。それ以外の価格差は付けない。
- 統合案の決定事項「1. 自サイトの価格方針」はこれで決定済み。

## 2. 商品が被る問題の扱い
- スクレイピングを行うPythonは、ショップごとに作る（共通の正規化マスターで一括統合する方式は取らない）。
- 収集結果はショップごとのシートに記載する。
- 出力するシートには階層を作る。出力が決定しているシートでは、重複するアイテムは表示されない（＝あるショップで出力が決まった商品は、他のショップ側では出てこない）。
- どのショップのものを採用するかは、価格などの条件面で判定する仕組みを作る。
- 収集の実行は、各ショップのPythonを順番に回す形とする。1個のPython（プログラム）で実現できるなら、その形が望ましい（2026-11-16追加）。

## 3. 追加決定（2026-11-16）
- 最上の（出力）シートでは商品は1つだけ表示するが、買い付け可能な他のショップも情報としてセルに入れておく。
- 原価計算は基本的にクーポン割引を適用した形で行う。クーポンの適用条件は各仕入先（ショップ）のシートに保存し、適用できるかどうかの判定に使う。
- このクーポンの決定は、統合案側の解消案（投入時はクーポン未適用で計算し、情報は記録のみ）より優先する。

## 4. 相談事項（2026-11-16追加）：情報を保存する仕組みはシートに限定しない
- 本人の言葉：「別にシートじゃなくても段階的に情報を保存できる仕組みがあればなんでもok。おれが昔のやり方しか知らないから。その辺りも相談したい」
- つまり上記の「シート」は手段の例示であり、要件は「ショップ別に分けて集める→条件で判定する→出力する」という段階的な保存と流れが実現できること。
- 各自、最適な保存の仕組み（ファイル／データベース／シート等の方式と、その理由・長所短所）を提案すること。

## 5. 追加決定（2026-11-16 11:15）：キッズ公開と在庫確認の頻度
- キッズ商品は公開する（本人の言葉：「キッズ公開して」）。
- 在庫確認は週2回行う（本人の言葉：「在庫確認は週二回」）。
- 残りの未決定事項：キッズのUSサイズ表記ルール、売り切れ表示（SOLD OUT表示か非表示か）、画像メインのルール。
