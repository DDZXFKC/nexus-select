## 2. `status_probe.py` の修正指示

### 指摘①：netstatの解析エラー

対象：12〜27行目

現行コード：

```python
if len(parts) >= 6:
    return parts[5]
```

macOSの一般的なIPv4ルーティングテーブルは、以下のような形式になる。

```text
Destination  Gateway       Flags  Netif  Expire
default      192.168.1.1   UGScg  en0
```

この場合、インターフェースは `parts[3]` にあり、そもそも6列存在しない。

実際のmacOSの出力例でも確認できる。

**GLMへの修正指示：**

単純に `parts[5]` を `parts[3]` に変更するだけではなく、デフォルトルートの取得には次のコマンドを使用する。

```bash
/sbin/route -n get default
```

出力の `interface:` を解析する。

IPv4とIPv6、複数のデフォルトルート、宛先別ルートは区別すること。コマンド失敗や解析不能は `UNKNOWN` として扱う。

### 指摘②：DISCONNECTEDの判定

対象：44〜87行目

魔王ちゃんの指摘どおり、`ifconfig -l` にutunが存在するだけではVPN接続中とは判断できない。

ただし、**デフォルトルートがen0であればDISCONNECTEDと判定する案にも反対する。**

AppleのVPN APIは、特定の通信だけをVPNへ流すスプリットトンネルをサポートしている。したがって、通常のデフォルトルートが物理インターフェースでもVPNが接続されている場合がある。

| 観測された情報 | 判断 |
|---|---|
| utunが存在する | VPN接続中とは断定できない |
| utunが存在しない | 対象VPNの切断を単独では証明できない |
| デフォルトルートがen0 | VPN未接続とは断定できない |
| デフォルトルートがutun | AHC DE・USのどちらかは不明 |
| ドイツの出口IPを取得 | AHC DEへの接続を単独では証明できない |
| 状態取得コマンド失敗 | UNKNOWN |

現行コードの65〜66行目では、`ifconfig` が失敗して空リストを返した場合も `DISCONNECTED` と判定する。

**これは今回の監査で最も危険な箇所の一つ。**

取得できなかった状態を「切断済み」と誤認すると、ウォッチドッグが復旧完了と判断し、リース情報を削除する可能性がある。

GLMには、エラーと正常な未接続状態を明確に区別するよう修正を求める。

### 指摘③：固定IPによる接続判定

対象：6〜10行目、78〜84行目

現在の実装では、今朝の実接続で観測されたDE・USの出口IPを固定値として登録し、完全一致した場合に接続成功と判定している。

しかし、VPNの出口IPが将来も同じとは限らない。

また、他のVPNや通信経路が同じ出口IPを使用した場合、AHC DE・USへの接続を誤認する可能性がある。

**GLMへの修正指示：**

- 固定IPを接続状態の判定条件にしない。
- VPNプロファイル自体の接続状態と、外部IP・出口国の確認を分離する。
- 実環境のIPアドレスは公開リポジトリにハードコードしない。
- `curl` の終了コード・HTTPエラー・タイムアウトを確認する。
- IPアドレスの形式検証にはPython標準の `ipaddress` を使用する。

現在の正規表現では、例えば `999.999.999.999` も受理してしまう。

なお、外部IP確認サービスへの接続失敗だけで、VPNが切断されたとは判断しない。

## 3. `shortcuts_backend.py` の修正指示

### 指摘④：ショートカットの実行失敗を成功として返す

対象：34〜49行目

現行コードでは、`subprocess.run()` の終了コードを確認していない。

Appleの公式資料では、ショートカットのCLIは成功時に0、エラー時に1を返すと明記されている。

現状では、終了コードが1でも以下の結果を返す。

```json
{
  "executed": true,
  "timeout": false
}
```

**GLMへの修正指示：**

実行結果を最低でも次の4種類に区別すること。

| 結果 | 意味 |
|---|---|
| COMPLETED | CLIが正常終了 |
| COMMAND_ERROR | CLIが異常終了 |
| TIMEOUT | 実行期限超過 |
| EXECUTION_ERROR | 起動そのものに失敗 |

ただし、CLIの正常終了をVPN接続成功と同一視しない。

### 指摘⑤：接続直後の状態確認が1回だけ

対象：51〜89行目

魔王ちゃんの指摘に全面同意する。

現行実装では、IKEv2の接続が確立する前に `probe_status()` が実行され、正常な接続処理でも失敗として扱われる可能性がある。

ただし、`connect()` 内に独自の長時間ポーリングを追加するだけでは、v2との統合時に問題が発生する。

v2には既に `wait()` がある。

**GLMへの修正指示：**

接続・切断命令と、状態が確定するまでの待機処理を分離すること。

1. **接続命令** — Shortcuts Backendが実行結果を返す。
2. **状態取得** — Status Probeが現在の状態を返す。
3. **ポーリング** — Controllerがリース残時間内で状態を確認する。
4. **成功または復旧** — 期限超過・失敗時は復旧処理へ移る。

待機時間はバックエンドで独自に決めず、Controllerから渡される期限に従う。

### 指摘⑥：実行結果が捨てられている

対象：56行目、77行目

```python
exec_result = run_shortcut(name)
```

取得した `exec_result` が、その後の判定に使用されていない。

これではタイムアウト、実行失敗、正常終了の違いがControllerに伝わらない。

実行エラーが発生しても、VPNが偶然目的の状態になっていれば成功を返してしまう。

**GLMへの修正指示：**

実行結果と観測した接続状態を両方返す。状態が一致したことだけで実行エラーを消さない。

また、接続先は明示的なDE・USの許可リストに限定する。デフォルト引数でDEを指定する現在の設計も廃止し、対象未指定時はエラーとする。

## 4. `preflight.py` の修正指示

### 指摘⑦：UNKNOWNでも準備完了になる

対象：29〜38行目

現行コードでは、状態取得が `UNKNOWN` であっても、4つのショートカットが登録されていれば `ready = True` になる。

**これは安全設計上、修正必須。**

状態が分からないままでは、切替前の接続状態を記録できず、ロールバック先も決定できない。

修正後は準備状態を分ける。

| 項目 | 意味 |
|---|---|
| shortcuts_registered | 必須ショートカットが存在する |
| diagnostic_ready | 読み取り診断を実行できる |
| profile_status_verified | 対象VPNの状態を正確に取得できる |
| recovery_ready | 復旧方式が検証済み |
| mutation_ready | 実際の回線変更を許可できる条件が揃った |

ショートカットが登録されているだけでは、`mutation_ready` をtrueにしてはいけない。

また、preflight単独で切替許可を発行せず、v2のウォッチドッグ確認・arm操作を維持する。

### 指摘⑧：インポートパス

対象：6行目

```python
sys.path.insert(0, '.')
```

現在の作業ディレクトリに依存しているため、LaunchAgentから実行した場合に別のモジュールを読み込む可能性がある。

GLMはこの行を削除し、同一パッケージ内のモジュールを確実に読み込む構成に修正すること。

通常のスクリプトとして配置するなら、スクリプト自身のディレクトリを基準にする。

## 5. v2との統合で発生する重大な問題

### 問題①：状態取得インターフェースが異なる

v2のControllerは、各VPNプロファイルの状態を個別に管理する構造になっている。

```json
{
  "DE": "Disconnected",
  "US": "Connected"
}
```

一方、GLMのv3では以下の4状態しかない。

```text
DE_CONNECTED
US_CONNECTED
DISCONNECTED
UNKNOWN
```

これでは、複数VPNの同時接続、他のVPNの接続、接続処理中、切断処理中を正しく表現できない。

**v3の状態取得インターフェースは、以下の形式に変更すること。**

```json
{
  "profiles": {
    "DE": "Unknown",
    "US": "Unknown"
  },
  "unmanaged_vpn": "Unknown",
  "exit_country": null,
  "network_reachable": null,
  "evidence": [],
  "errors": [],
  "verified": false
}
```

これは状態取得に失敗した場合の出力例。

接続状態を取得できなければ、推測で `Connected` や `Disconnected` を設定しない。

### 問題②：ウォッチドッグが外部通信に依存する

v2の設計では、インターネットとの通信が途絶えても、ローカルでVPNの状態を取得し復旧することを前提としていた。

ところが現行のv3は、`curl` で外部IPを取得できなければ状態を判断できない。

```text
VPN切替に失敗
  ↓
インターネット通信断
  ↓
外部IP確認に失敗
  ↓
VPN状態がUNKNOWNになる
  ↓
自動復旧を確認できない
```

現在の実装では、復旧が最も必要な場面で状態取得が機能しなくなる可能性がある。

これでは安全装置として成立しない。

**VPNプロファイルの状態確認は、外部通信なしで動作することが必須。**

外部IP確認は、回線復旧や接続確定のための補助的な検証として扱う。

### 問題③：タイムアウトしたショートカットの遅延実行

例えば、接続ショートカットが30秒でタイムアウトした後、裏側の処理が継続していたとする。

ウォッチドッグが元のVPNへ復旧した後、遅れて切替先VPNへの接続が成立すると、再び通信が途絶える可能性がある。

GLMは、次の条件を満たす設計にすること。

- 実行中の操作を永続的に記録する。
- タイムアウト時に、VPN操作自体が停止したとは判断しない。
- 状態が確定するまで新しい切替を禁止する。
- 復旧後に遅延した操作が発生しないか検証する。
- 復旧を証明できなければ `pending.json` を削除しない。

### 問題④：リース時間の超過

現行コードは、ショートカットの実行に最大30秒、各utunのIP確認に最大10秒を費やす。

utunが複数存在すると、それだけで既存リースの期限を超える可能性がある。

その間、Controllerが排他ロックを保持していれば、ウォッチドッグも復旧処理に進めない。

すべての外部コマンドに共通の時間予算を設定し、リース期限を超えて新しい切替処理を開始しないこと。

復旧処理には切替処理とは別の時間予算を用意し、失敗時も復旧記録を保持する。

## 6. 最大の課題を先に解決する

今回のコード監査で改めて分かったのは、ショートカットによる接続・切断よりも、**正確なVPN状態の取得の方が難しい**ということ。

Appleの公式資料を確認したところ、「Get Current VPN」「Find VPNs」は新しいOS向けの追加アクションとして案内されている。macOS 15で利用できる機能として前提にしてはいけない。

したがって、GLMには次の順序で進めてもらいたい。

| 優先順位 | 作業 |
|---:|---|
| 1 | macOS 15.8.2でプロファイル別の状態取得方法を確立 |
| 2 | Status Probeの誤判定修正 |
| 3 | Shortcuts Backendの実行結果・期限管理修正 |
| 4 | Preflightの安全判定修正 |
| 5 | Controllerとの統合 |
| 6 | 模擬環境での回復・異常系テスト |
| 7 | iMacでの監督下の実機テスト |

状態取得方法の候補として、システム設定のVPN状態を読み取り専用で取得できるか検証する価値はある。ただし、アクセシビリティ権限が必要になる可能性があり、未検証の方法を採用済みとして扱わない。

信頼できる状態取得方法を確立できなければ、VPN切替機能は読み取り・手動運用の段階に留める。
