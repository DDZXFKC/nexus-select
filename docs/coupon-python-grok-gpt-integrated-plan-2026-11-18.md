## 最小実装順（余計な開発をしない）
1. L0 正本参照。商品収集側の既存資産を先に確認し、shop_code + market + 根拠/承認状態のスナップショットを読み取り専用で返す。買付対象・承認済み候補・対象外を区別。空/取得失敗は全許可禁止。対象の追加削除を正本から反映し別マスターを作らない。
2. L1 取得/保存入口。対象店舗別に許可された取得のみ。総合feedは受信直後、dedup/validate/DB前に判定。対象外は即除外、未特定は容量制限つき確認キュー（運用未確定なら件数と理由だけを記録して本流へ流さない）。共通allowlistガードをbridgeにも置く。対象削除時の旧候補を読み取りから遮断。既存価格ゲートの処理は変更しない。実測呼出側も対象確認。
3. L2 明示失効・市場不一致・確実な対象外条件・重複を安価に処理。未知は保留。金額は取り込み境界でDecimal→通貨別minor整数へ正規化、USD/EUR/GBP=2、JPY=0。不正/欠損/通貨不一致はUNKNOWN。最低額を下回ればEXCLUDED。既存の価格・原価契約を維持。
4. L3 A軸は公式証拠、明確な失効、独立した最近の同条件成功に限定。証拠が足りなければDISCOVERED/保留。複雑なスコア不要。未知の出所を独立成功に数えない。公式と第三者の矛盾は公式の有効条件優先、解消不能なら保留。新旧キャンペーンの区別がつかない場合は混ぜず保留。
5. L4 B軸は明示除外優先、条件の完全性が証明されなければUNKNOWN。明示無制限と未取得を区別。未知を除外とも適合とも断定しない。
6. L5 C軸は既存select/record_checkの厳格契約を共有し、完全scope・期限・同時刻矛盾・新観測を確認。確認作業と実測は別。Grokの「MATCHのみ」は確定割引評価の入口として採用するが、UNKNOWNは捨てず、規約確認で解消できる場合だけ限定確認キューへ。UNKNOWNのまま確定価格に使わない。ライブ取得、カート操作、購入、価格反映の承認は別。
