## 1. 横断キーの最終仕様（Q1）

### 1.1 定式化：末尾検索方式の採用と8字則の処遇

- **実装するのは1つだけ**：`FL(数字コア, 色コード)` について、同一ブランド内で「SP色コードと完全一致 かつ SPスタイル番号が数字コアで終わる（コア3字以上）」→ 一意なら採用。
- **8字則は併記するが実装しない**。理由は2点：(i) `130BBLC`（7字）が厳密な8字不変量の反例、同一スタイル1155130でk=4とk=3が混在することから、SP→FLの**生成規則は存在しない**（照合はFL→SP単方向でのみ成立）。8字則は「FL側が概ね8字フィールドからコードを刻んでいるらしい」というREADMEレベルの説明として残し、照合ロジックからは完全に分離する。
- **kの上限を設けない**。コアが長いほど証拠は強くなる（危険性は下がる）ため、規制すべきは下限のみ。UGGの全桁保持（3236→3236CHE）もendswithの特殊ケースとして追加条件なしで扱える。

### 1.2 FL側パース規則（大文字正規化後）

```
HOKA/UGG:
  ^(\d{3,})([A-Z]{2,})$ → core, color に分割 … 自動照合経路
  ^\d+$（数字のみ）        → HOLD_LEGACY_NUMERIC（2072001, 42110519）
  先頭に英字等の接頭辞      → HOLD_NO_COLOR 系経路（AR422710, H011RRCK, UG461450）。純数字の42接頭辞列はLEGACY（分解禁止）
Vans:
  接頭辞を longest-first（VN → 00 → V → 0）で1回だけ剥離（先頭アンカー、反復剥離禁止）
  残りをSPコードと完全一致照合 … 自動照合経路
```

### 1.3 SP側インデックス

- **一次インデックス**：`(brand, color_code) → [style_numberのリスト, 各styleにsellableフラグ]`
- **Vans用**：`(brand, code) → SPアイテム`
- **重要**：インデックスは**スクレイプ元CSV全件**（sellable 163件ではなく全スタイル）で構築する。sellable集合はランごとに変動するため、一意性判定を現行sellableのみで行うと「今日一意・明日曖昧」が発生する。**曖昧性判定は全コーパス基準**が前向きの衝突対策になる。

### 1.4 照合手順（擬似コード）

```python
cands_all  = [s for s in index[brand, color] if s.style.endswith(core)]
cands_sell = [s for s in cands_all if s.sellable]

if len(cands_all) >= 2:            HOLD_AMBIG          # 全コーパスで曖昧
elif len(cands_all) == 1
     and len(cands_sell) == 1
     and len(core) >= 3
     and len(core) + len(color) >= 7:
                                     AUTO(link)          # TAIL3/価格/名称はタグのみ
elif len(cands_all) == 0:           NO_MATCH            # SP側に候補なし（正常系）
# 全AUTO確定後：同一SPを指すFL行が複数あれば全員 HOLD_COLLISION
```

照合順序は**色コード完全一致を先に（選択性の主要源）**、endswithをその後。色コード一致は自動採用の必要条件（ハードゲート）であり、これがtail-3を安全にする唯一的な担保。

### 1.5 先行ゼロの扱い

**endswithの文字列比較で吸収する方式でよい。数値化は禁止。** `0518BBLC` と `518BKSTR` の混在は、文字列suffix比較なら両方自然に拾える。int変換すると `0518`→`518` の潰れで偽陽性の余地が生じる。全比較は「大文字化・トリム済み文字列」で行う。

### 1.6 優先順位と再実行

- 照合の優先順位：**手動対応表 → 法則（自動）**。対応表エントリは法則に優先する。
- 毎ラン、FL全268件（現行販売可能全体）に冪等に再実行。ティアの昇格/降格はログに残す。

## 2. 例外処理（Q2）

### ステータス体系（確定）

| コード | 対象 | 処理 |
|---|---|---|
| `HOLD_TRUNCATED` | 00ZB8CD | **手動対応表に登録して解決**（ZB8CDA↔00ZB8CD）。1事例からの一般化（「FL=SP末尾1字欠落も許容」）は禁止——緩い一致は誤爆源 |
| `HOLD_NO_COLOR` | AR422710, UG461450, H011RRCK | 名前補助可：**数字末尾一致＋モデル名トークン一致（"Bondi 7"等）で候補提示→人目確認→対応表登録**。自動リンクは不可 |
| `HOLD_LEGACY_NUMERIC` | HOKA 42110519等13件・UGG 2072001等3件・Vans 11件 | コード体系が別系統。**対応表のみ**（後述の登録規則による）。現在SP側対抗なしにつき実質終端状態、毎ラン再評価 |
| `NO_MATCH` | VN000EFG等、SP未掲載 | **HOLDではなく正常系の未一致**。「法則が不成立」ではなく「SP側に商品がない」。241件はこちら |

### 名前補助の範囲

- 許可：HOLD_NO_COLOR の HOKA/UGG のみ（末尾一致があるため名前は補強に回る）。
- 不許可：Vans旧数値コード（モデル名の同質性が高く、色がないと候補が爆発するため、名前補助でも自動化せず純手動）。

### 手動対応表

- スキーマ：`brand, fl_code, sp_style, sp_color, match_type(MANUAL_TRUNCATED / NAME_CONFIRMED), evidence_note, created_at`
- **登録規則：人手で同一カラーウェイを確認した対のみ登録。推測では登録しない。** 現時点のシードは ZB8CDA↔00ZB8CD の1件のみ。色なし3件・旧数値12件は確認が取れた時点で初めて登録する。

## 3. 自動採用の最終線引き（Q3）

### 3(a) 末尾3桁：条件付き自動採用可

**AUTO条件（HOKA/UGG）＝一意性＋強度の掛け算**：

1. 色コード完全一致（ハードゲート）
2. コア≥3字
3. **コア＋色コード≥7字** ← 今回新設の強度下限
4. 全SPコーパスで候補1件（sellable一意だけでは不十分）

条件3の帰結として、**色コード3字（BLK/CHE等）ではコア4字以上が要求され、コア3字＋色3字の6字キーのみが `HOLD_SHORT_KEY`（旧HOLD_TAIL3の置換・縮小版）に残る**。現データでは該当0件。既存3件（130BBLC=3+4, 518BKSTR=3+5, 910BKSTR=3+5）は全て≥7字かつground truth確認済みにつき**AUTO昇格**。ただし `TAIL3` タグを付し、通常の5%抽選点検ではなく**毎四半期の全件点検**対象とする（3件なのでコスト無視できる）。

### 3(b) D9RCCZ：コード法則が名称を上回る

- **原則として確定**：名称はプラットフォーム間で規約が違う（SP=マーケ色名／FL=色記述）ため、**コード法則＋一意性が成立している場合、名称不一致は門ではなく注記（ADV_NAME_NOTE）**。本件はground truth入りなので即AUTO化。
- HOLD_NAME_CONFLICT は**名前補助経路（名前が主証拠の経路）のみ**に残置する。
- 逆に名称一致は正面証拠として使い続ける（点検キューの優先度に反映）。

### 補強トリップワイヤ（非ブロッキング）

- `ADV_PRICE_DELTA`：既知セール5件を除き |ΔUSD| > $5（設定値）のAUTOペアは点検キュー行き。今回の実証で価格差が誤マッチのカナリアとして機能したので、これを常設する。
- ログ専用：FLコード9字以上、ヘッド落下5字以上（観測範囲は0〜4字）。ゲートにはしない。

## 5. 残リスクと再検証トリガー

1. **SP母数増加に伴う衝突**（同一ブランド・同色コード・同末尾の別スタイル）：全コーパス一意性判定で前倒し検知。`HOLD_AMBIG` 発生率を監視し、初発生時に本仕様を見直す。
2. **色コード内数字の出現**：HOKA/UGG色コードは現在全て英字。パース正規表則（数字→英字の1回切り替え）はこの前提に依存するため、英字部がSP色と一致しないケースは自動的にNO_MATCHになり害はないが、検知したらログに残す。
3. **再検証タイミング**：SP全コーパスが+50件超えるごとに確定ペアの再検証、四半期ごとにTAIL3・ADV_*タグ全件点検。
